Workflow examples

Five common situations, step by step, with the exact commands. The examples use research repos; the names are only illustrations.

Workflow 1

New repo from scratch

You start a benchmark of clustering methods on simulated data. Nothing exists yet.

Uses: You/setup-workflow then workflow 2
Session 1 · day 1
  1. You

    Create the repo on GitHub first: the workflow needs a GitHub remote, because every task has an issue.

    gh repo create sim-bench --private --clone
cd sim-bench
  2. You

    Open Claude in the folder, as a new session.

  3. /setup-workflow

    Claude looks at the folder (git? GitHub remote? existing files?) and asks two things, with recommended answers:

    Project in one line? "Benchmark of clustering methods on simulated data."
    Language and tools? "R, renv, Slurm on the cluster."

    It shows you the drafts. You ask for changes until they look right; then it writes them and makes one commit, workflow: plans/PROGRESS setup. It does not push.

  4. You

    Push when you are ready: git push -u origin main (or ask Claude to).

  5. /new-plan

    Your first task starts here, exactly as in workflow 2. Often the first task is "set up the project skeleton" or the first analysis.

The folder after setup

sim-bench/
├── CLAUDE.md               + a short section: read plans/README.md, start from PROGRESS.md
├── README.md               + "Development workflow": the flow and a link to the rules
├── PROGRESS.md             folder log: Current state "no active task"
├── plans/README.md         all the rules: build, issues, review, plan changes, logs, statuses
└── .gitignore              tmp/ ignored

GLOSSARY.md appears later, when you agree on the first key term.

Workflow 2

New task from your head, in an existing repo

In a repo already set up, you have an idea: try a hurdle model for the zero-heavy taxa. Nothing is written down yet.

Uses: /project-refresher/new-plan/progress
Session 1 · day 1
  1. /project-refresheroptional

    Check that nothing else is half done (uncommitted files, another active task) before you start something new.

  2. You

    Talk the idea through in plain words: what you want, why, what you already know, what worries you. Stop whenever you like; nothing needs to be settled.

  3. /new-plan

    Every task has a GitHub issue. You name one, or Claude creates it with gh issue create: the title, and a body that is only the problem in 2-3 lines (the issue says why, the plan says how), e.g. #41. Folder and branch: issue-41-hurdle-model.

    Then Claude:

    • reads the code and data the idea touches, so Where things are now is correct;
    • writes the draft to tmp/new-plan/issue-41-hurdle-model/PLAN.md and gives you the path: a short Goal, maybe a few steps, and everything unsettled under Open questions;
    • changes the file until you approve; you can edit it too. Nothing goes into git before your yes.

    Then Claude creates the branch from an up-to-date main, moves the draft into the task folder, logs any decisions you already made as DECISION lines, and commits plan: start issue-41-hurdle-model. It asks before pushing; once pushed, it puts the plan link in the issue body.

    status drafting
  4. /progress

    At the end of the session, if anything is not logged yet (or say "log progress"). The task log gets Next, e.g. "decide open question 1: how to model the zeros". The folder log only gets status changes, PRs and work outside a task, so it stays short.

What you have now

plans/issue-41-hurdle-model/
├── PLAN.md       Goal · Where things are now · Steps · Open questions
└── PROGRESS.md   **Status:** drafting · Current state · Next · entries

Next: keep working on the draft over the next days, as in workflow 4.

Workflow 3

Start on an existing GitHub issue

Issue #27, "Simulator ignores coverage below 5x", is open. Maybe you wrote it weeks ago, maybe someone else did.

Uses: /new-plan/finalize-plan/implement-next/progress
Session 1 · plan
  1. /new-plan
    You: "/new-plan for issue #27"

    Claude reads the issue, its body and comments (gh issue view 27 --comments), and the code it names. Then it drafts PLAN.md in tmp/new-plan/: the Goal comes from the issue, and points left open in the comments become Open questions. After your yes, it creates issue-27-low-coverage from main and commits. After you push, the plan link goes into the issue body.

    status drafting
  2. You

    Decide if the plan needs more thinking:

    Clear and small

    The issue already says what to do. Run /finalize-plan now, in the same session.

    Needs thinking

    Run /progress, stop, and keep drafting over the next days as in workflow 4.

  3. /finalize-plan

    Claude checks each item and shows ok or gap: Goal, Open questions, files that really exist, steps concrete enough, decisions written in the plan, the issue (title matches the plan, no solution text), and the build shape (each step one commit, or a big step with sub-steps). You fix the gaps (or accept them), then:

    "Set the status to planned?" You: "yes"
    status drafting → planned

    Then Claude shows the GitHub structure the plan implies, and creates it after your yes: a checklist of the plan's steps in the issue body, and a sub-issue with its own branch for each big step (none here: three small steps).

Session 2, 3, … · build (always a fresh session)
  1. You/project-refresher

    Run /clear or open a new session, then the refresher. It shows the task's Next, e.g. "PLAN step 1: add the coverage filter in R/simulate.R".

  2. /implement-next

    Claude builds the next unchecked step. Before the commit it reviews the change: /code-review for bugs, then Spec (against the plan step), Research (lost rows, missing values, units, seeds, numbers that look wrong) and Style. Then one commit for the step, with the log update in it (what was done, DECISION lines, a new Next), and it ticks the box in the issue. Running it on the first step is your choice to start:

    status planned → in-progress

    If reality breaks the plan, say so. Claude shows the change to PLAN.md, and after your yes logs it as a DECISION line with the (plan change) tag and what the plan missed.

Last session · close
  1. /code-reviewYou

    When every box is ticked: the same review on the whole branch, then the PR into main (gh pr create, or ask Claude to). Check that the PR description says Closes #27, so merging closes the issue. You merge it.

  2. /progress

    When the PR is merged, tell it "merged, mark done". The plan link in the issue now points to main. The folder log gets a one-line summary and the task leaves Current state. The task's Next becomes "None"; what comes after goes in the folder log's Next.

    status in-progress → done
Workflow 4

Continue a plan that is still a draft

The hurdle-model plan from workflow 2 is in drafting. You come back to it on a new day, maybe a week later.

Uses: /project-refresher/grill-plan/sandbox/progress/finalize-plan
Any brainstorm session · repeat as many days as needed
  1. /project-refresher

    In a new session. Add detailed to also see the open questions and the last decisions.

    # At a glance
Drafting the hurdle-model plan (#41); stopped after ruling out zero-inflated NB.
## Next step
Decide open question 2: which zero process to use.
  2. You

    Brainstorm on that question: plain talk, or /grill-plan if you want to be pushed (Claude asks about the plan in rounds, each question with a recommended answer, and looks up facts itself). Ideas can go off in any direction; nothing is lost as long as /progress runs before you stop.

  3. You/sandbox
    You: "I want to see how the zero fraction depends on read depth before I decide."

    Claude writes plans/issue-41-hurdle-model/sandbox/03-zero-fraction.R (sections you run one by one, each with a Look at: note), runs its setup once to catch typos, and tells you what to open. You run it and look at the plots. Its outputs go to tmp/sandbox/, never your real results.

    You: "Zeros are about 80% in samples under 5k reads, and flat above that."

    Claude fills in the sandbox Findings.

  4. You

    Say what should change, whenever it should: after a decision, a new idea, or a new question. Claude shows the changes to PLAN.md (question 2 removed, a new step added), and you approve. The decision goes in the task log:

    - **DECISION 2026-11-04 15:10:** model zeros with a depth-dependent hurdle, because the zero fraction falls with read depth up to 5k (sandbox 03)

    While drafting, the plan is edited freely, and a plan change never changes the status. The rules are in plans/README.md.

    status stays drafting
  5. /progress

    Before you stop. The task log gets what you explored, any decisions not yet logged, and a new Next (e.g. "open question 3: random effects for batch?"). The folder log is not touched.

The day you think it is ready
  1. /finalize-plan

    If weak spots remain, Claude first offers /grill-plan. Then it shows each item as ok or gap. Example gap: "Open question 3 still open". You either settle it now (Claude edits the plan under the plan-change rules) or accept it as an assumption the build can start with. Then, only on your "yes":

    status drafting → planned

    From here, building is the same as the build sessions in workflow 3.

  2. Youlater, if needed

    Once the plan is agreed, a decision that changes it is logged with the (plan change) tag and what the plan missed. A new open question after the plan is planned or in-progress? Claude asks once:

    "Keep the status, or go back to drafting?"

    Both answers are fine. Mid-build with one question open is normal in research.

Workflow 5

Run an experiment

You want to know if a hurdle model beats zero-inflated NB on the simulated benchmark before you touch the main code. It will be messy: scripts, cluster runs, plots in the console.

Uses: /new-plan exp/finalize-plan/write-results/progress optional /sandbox
Session 1 · start
  1. /new-plan
    You: "/new-plan exp", or say in words that it's an experiment.

    Without "exp", /new-plan makes a normal task. The issue question works as in workflow 2; a good issue title is the question itself. The experiment can use any language or tool. Only analysis.qmd has a default, R; ask for Python if you want it.

    PLAN.md gets objectives instead of a Goal:

    ## Overall objective
Decide if a hurdle model should replace ZINB for zero-heavy taxa.

## Specific objectives
1. Is FDR lower at equal power? Answered by results/fdr_power.csv (stage: summarize).
2. How does runtime scale with sample size? To decide.

    Claude also creates the experiment's parts from templates:

    plans/issue-52-hurdle-vs-zinb/
├── PLAN.md  PROGRESS.md     **Kind:** experiment
├── experiment/run.sh        the one entry point (stages to fill)
├── results/                 small figures and tables, committed
├── RESULTS.md               skeleton, filled at the end
└── analysis.qmd             skeleton, filled at the end
    status drafting
  2. /finalize-plan

    After drafting (same as workflow 4, as long as you need). For an experiment it checks that the overall objective is there, that each specific objective says how it will be answered, and that run.sh names the planned stages, even if they are empty.

    status drafting → planned → in-progress when you start
The messy middle · many sessions
  1. You

    Work in experiment/ any way you like: run scripts directly, try things in the console, use /sandbox for side questions. Two rules only: don't change the main code from here (a change it needs is its own commit, named in the log), and keep big outputs in $OUT, never in git.

  2. You

    As each part settles, it becomes a stage in run.sh (see run.sh, explained below). Stages can call anything:

    ./run.sh                          # list the stages
./run.sh simulate fit             # run two stages
OUT=/scratch/$USER/hurdle ./run.sh fit   # big outputs on the cluster's scratch

    Every run adds the commit, uncommitted changes, host and stages to $OUT/run-info.log. That is where the provenance in RESULTS.md comes from.

  3. /progress

    As in any task: the log goes in the same commit as the work, with DECISION lines and job IDs. If an objective changes, say so; once the plan is agreed, the DECISION line gets the (plan change) tag, and RESULTS.md will list the changed objective.

Close · one or two sessions
  1. /write-results

    The first round writes the whole draft from the outputs and the log: Answers (high level, one per objective), a brief Methods, detailed Results with the figures and tables in results/, a very short Discussion and conclusion, and the Appendix: what is where (every path, what it is, which stage made it, whether it is in git, and the commit, environment, data and job IDs). Every number names the file it comes from.

    It also writes the short analysis.qmd: load the main objects, show one or two main results, then "continue from here". You run it chunk by chunk in RStudio, Positron or VS Code, and keep playing in it whenever you like.

    Every section it writes is marked <!-- unreviewed --> under its heading.

  2. You/write-resultsrepeat, any order

    Then you go round as often as you need, in any order, always with the same command:

    /write-results                  update the draft after new runs
/write-results results 2        redo one section
/write-results interpret        propose the discussion and conclusion
"Methods is fine. In Results 1, report the median, not the mean."

    A section loses its unreviewed mark only when you say it is reviewed. Text you edit by hand is never overwritten. Interpretation stays in Discussion and conclusion, and is a proposal until you review it. Each round is logged in one line, and the answer to the overall objective becomes a DECISION line.

    Claude, after a round: "Changed: Results 2, Discussion. Still unreviewed: Results 2, Discussion. Ready to close when those are reviewed."
  3. /progress
    You: "mark done"

    Because the task is an experiment, Claude first runs the close check and lists what is missing:

    RESULTS.md     ok   5 sections, no placeholders, all reviewed
Appendix       gap  results/runtime.png has no stage
run.sh         ok   parses, lists 4 stages (nothing re-run)
analysis.qmd   ok   setup chunk runs
DECISION       gap  no final answer line yet

    You fix the gaps (or accept them, and they are named in the log). Then the final DECISION line and the status change:

    - **DECISION 2026-11-20 16:40:** ruled out the hurdle model, because FDR was not lower on 5 of 6 settings (RESULTS.md, results/fdr_power.csv)
    status in-progress → done (a "no" is still an answer)
  4. You

    Open a PR and merge it. Always merge, whatever the answer, so the record lands in main. It is safe: the experiment never changed the main code.

  5. /new-planif the answer is yes

    Putting the winner into the main code is a new, normal task ("integrate the hurdle model"), linked to the experiment's final DECISION line.

run.sh, explained

You don't need to know bash. The file has three parts, and you only edit the middle one. Each stage is a name, then (), then a block in { } holding the commands you would type in the terminal. For this experiment, part 2 could be:

simulate() {
  Rscript simulate.R "$OUT/sim"                     # writes simulated data (big)
}

fit() {
  sbatch --wait fit.slurm "$OUT/sim" "$OUT/fit"     # cluster job; waits until it ends
}

summarize() {
  Rscript summarize.R "$OUT/fit" "$RES"             # writes fdr_power.csv and 2 figures (small)
}

all() {
  simulate
  fit
  summarize
}

How to read it:

  • "$OUT" and "$RES" are the two output folders (next box). Always keep the quotes around them.
  • Everything after # is a comment.
  • ./run.sh simulate fit runs those two stages in order. ./run.sh all runs the all stage, which calls the others. ./run.sh alone only lists the stages.
  • Your scripts can read the folders too: Sys.getenv("OUT") in R, os.environ["OUT"] in Python.
  • Part 1 (setup) stops at the first error and finds the folders. Part 3 (runner) checks the stage names and, before each run, adds a line to $OUT/run-info.log: date, computer, stages, commit, uncommitted files. That log is the provenance for RESULTS.md.

Which outputs go to git

Nothing is chosen by file size. The folder a stage writes to decides it, and you choose the folder when you write the stage:

$RES  = plans/<task>/results/       committed      what RESULTS.md shows: summary tables, final figures
$OUT  = tmp/experiments/<task>/     not in git     everything else: simulated data, fits, intermediate files
        (or OUT=/scratch/... on the cluster)

The rule of thumb: if RESULTS.md shows it, write it to $RES; otherwise, write it to $OUT. tmp/ is gitignored, and a scratch folder is outside the repo, so nothing in $OUT can reach git by mistake. The Appendix of RESULTS.md lists both kinds, so you can always find a big output again.

If you stop without an answer

Tell /progress "drop it". You need only a short RESULTS.md: what was tried, what was seen, and why it stopped. No analysis.qmd. The status becomes dropped, and the folder is still merged as history.
